# Spec Delta

## Purpose

定义模块二数据库、Spring Boot、Vue 和 Dify 的一体化交付基线，确保跨仓实现遵守"复用模块一研究入口 + 新增 13 表"、Dify 只产草稿、研究 70 分制、候选只交接模块三以及一期 Paper/真实交易隔离原则，并能按契约验收。

## ADDED Requirements

### Requirement: 跨仓实施必须遵守统一权威边界
后端、前端和数据库实现 SHALL 以 MySQL 业务主库、Spring Boot 事实源、Dify 草稿层和 RuoYi 权限事实源为唯一边界；模块二不得直接创建策略信号、交易计划、Paper 订单或真实交易能力。

#### Scenario: 代码提交包含跨域直写
- **WHEN** 模块二代码尝试从 Controller/Dify/筛选任务直接写策略触发、Paper 订单、资金、持仓或风险状态
- **THEN** 架构检查或代码评审拒绝该实现，并要求通过模块三交接/模块四契约

#### Scenario: 前端请求 Dify
- **WHEN** 浏览器尝试携带 Dify Key 访问 Dify API
- **THEN** 请求被架构/网关边界拒绝，前端只能调用 Spring Boot 研究接口

### Requirement: 研究候选用户路径可恢复
系统 SHALL 支持普通用户低输入研究并查看候选/研究卡、审核用户核验事实与研究卡、候选交接模块三；任一步骤失败、超时或页面离开后，状态、版本、幂等键和下一步必须可恢复。

#### Scenario: 普通用户从研究到研究卡
- **WHEN** 用户选择对象、问题与周期后提交研究任务
- **THEN** 系统创建带快照与幂等键的任务并展示事实/解释/预测分层与生成的研究卡，不要求用户填写评分、公式或风险参数

#### Scenario: 交接被退回后可恢复
- **WHEN** 候选交接被模块三拒绝并要求补充
- **THEN** 系统保留交接回执与原因，候选回到待补充状态并可从原版本继续，不重复创建交接副作用

### Requirement: 数据库、代码目录和 UI 契约必须一致
数据库表、后端实体/接口、前端 API/页面和 Dify 草稿字段 SHALL 使用同一业务对象、状态、版本与权限语义；研究评分只承载模块二 70 分贡献，任何不一致必须在契约或设计审查中被发现。

#### Scenario: 研究卡字段对拍
- **WHEN** 后端研究卡 DTO、数据库 `research_card` 表与前端研究卡类型完成构建
- **THEN** 卡 ID、版本、方向、机会状态、多周期预期与统计字段可相互映射，缺失或类型不一致使契约检查失败

#### Scenario: 研究分不被当总分
- **WHEN** 候选研究分被用于评估进入观察或生成 Paper 计划
- **THEN** 该分只作为模块二 70 分制子分，必须等策略/执行/风险维度合并后按总门槛评估，单方放行被评审拒绝

### Requirement: 一期边界和联调门禁可验证
实现 SHALL 明确一期仅 A 股/国内期货、日线主流程、施工期 Mock、Paper/Shadow 隔离和真实交易禁用；联调必须在 JDK21 + Maven 后端和 pnpm 前端启动后执行。

#### Scenario: 一期能力扫描
- **WHEN** 对菜单、路由、API 和构建产物执行能力扫描
- **THEN** 不存在分钟/Tick 盘中交易、LIVE、QMT、CTP、真实 Broker submit/cancel 或候选直达下单路径

#### Scenario: 前后端联调
- **WHEN** 后端以 JDK21 + Maven 启动 `DromaraApplication`，前端执行 `pnpm dev`
- **THEN** 用户可完成研究任务→事实核验→候选/研究卡→审核→交接回执流程，Dify 可校验/降级，且现有 Paper 回归测试继续通过
