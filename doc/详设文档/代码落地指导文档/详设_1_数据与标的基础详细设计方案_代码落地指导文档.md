## 一、提案信息与文档定位

### 1.1 本模块要回答什么

模块一是 QuantPF 的**确定性数据底座**。它不判断“标的是否值得买”、不生成策略信号、交易计划或订单，只向下游（研究、候选、策略、风险、回测、Paper）提供可追溯、可核验的数据、明确的标的身份、制度状态与用途资格。

核心链路（《详设_1》结论）：

```
供应商/来源组配置 → 授权与用途确认 → 新闻/行情/规则数据采集 → 原始快照与哈希去重
→ 字段/单位/时间/标的标准化 → 质量/冲突/授权/点时治理
→ 标的身份、A股/港股/美股/期货日历、外汇时段规则、公司行为与合约事件
→ 市场本地日期/时区、日线数据就绪、市场状态、容量与用途资格
→ 新闻研究任务 → Dify/TradingAgents 分析草稿 → Spring Boot 校验 → 研究事件发布
→ 向研究/策略/风险/回测/Paper 提供合格输入
```

### 1.2 职责主边界（不可越界）

- **Spring Boot**：事实源与确定性主系统——采集、保存、核验、版本、身份、Tushare 原始字段适配、交易日历、时段规则、外汇品种规则、质量、事件、状态、下游通知。
- **Dify/TradingAgents**：只能生成「数据文档解释 / 研究草稿 / 问答」，**禁止**直连数据库、修改原始数据/来源/授权/身份/质量、写研究事件主表、生成订单副作用。
- **Vue**：配置、查询、确认、处理冲突、接收告警；普通用户默认只看到「可用/为什么/下一步」三层展示。

### 1.3 一期硬约束

1. 原始数据、结构化数值、点时版本、研究事件、量价特征主记录**不放在** Dify/TradingAgents 数据库或向量库。
2. 用途资格（DISPLAY/RESEARCH/SCREENING/STRATEGY/BACKTEST/PAPER/RISK_MONITORING_ALLOWED）**分开判断**，由确定性规则计算。
3. 任何数据修订保留旧版本（不允许静默覆盖）。
4. 所有写操作幂等、可审计、可回放。
5. 禁止 LIVE/QMT/CTP 真实 submit/cancel（契约 `forbiddenCapabilities` 已固化）。
6. 施工期数据源用 **Mock + 单元测试**打通；Tushare 2000 积分套餐在代码完成、联调前购买；新闻源（财联社/新浪/雪球）当前未授权，状态从 `PENDING_CONFIRMATION` 起步。

## 三、系统架构扫描结论（来自实际代码仓）

### 3.1 后端架构模式

- **形态**：单体 + Maven 多模块（ADR-1）。入口 `ruoyi-admin`，业务模块 `quantpf-modules/*`，底座 `ruoyi-common/*`、`ruoyi-modules/*`、`ruoyi-api`、`ruoyi-extend`。
- **框架栈**：Spring Boot 3.5+（JDK 21，可选虚拟线程）、MyBatis Plus 3.5.17、Sa-Token、springdoc(knife4j)、EasyExcel、hutool 5.8.47、lombok 1.18.48、redisson 4.7.0（lock4j `@RepeatSubmit`）、easy-es 3.0.2（elasticsearch 7.17）、SnailJob 2.0.2（ADR-10 迁移至 XXL-JOB 3.1.0）、mapstruct-plus、LiteFlow 2.16.2。
- **MVC 分层（底座标准，`org.dromara.system` 为参照）**：`controller`（继承 `BaseController`）→ `service`/`service/impl`（继承 `IService`/`ServiceImpl`）→ `mapper`（继承 `BaseMapper<Entity>`）→ `domain`（`entity` 继承 `BaseEntity`、`bo`、`vo`）。`event`/`listener` 处理领域事件。
- **统一响应**：`org.dromara.common.core.domain.R<T>` 与 `PageResult<T>`；分页用 `org.dromara.common.mybatis.core.page.PageQuery`；导出用 `ExcelBuilder.of(...)`。
- **主键策略**：MyBatis Plus 全局 `idType: ASSIGN_ID`（Snowflake）。但**业务表主键名按规范统一为 `pk_id`**（详见 §五/§六），由 Hutool `IdUtil.getSnowflake(workerId, datacenterId)` 生成，workerId/datacenterId 走 YAML/env。

> ⚠️ **风格分歧说明（重要）**：`quantpf-modules` 现有已落地代码（`quantpf-domain/execution/finance/risk`）采用早期 **DDD 六边形 + 原生 MyBatis（Mapper 接口 + XML + Record）** 风格，主键为 `id BIGINT AUTO_INCREMENT`。这与底座 `org.dromara` 的 **MVC + MyBatis Plus + Lombok** 标准不一致。《详设_1 §22.1》明确“控制器不直接写表、只定义仓储端口/领域边界”属于领域模块设计约束，但**接口层（Controller/Service）与持久化层必须向底座 MVC + MyBatis Plus 标准收敛**。本指导文档按底座标准描述新代码；既有 quantpf 代码只在“扩展既有表/能力”时定点修改，不整体重写。

### 3.2 前端架构模式

- 技术栈：Vue 3.5 + TypeScript 6 + Element Plus 2.14 + vxe-table + ECharts 6 + UnoCSS + Pinia + vue-router。
- 目录：`src/api/**`（按域拆 `index.ts` 接口 + `types.ts` 类型）、`src/views/**`（页面）、`src/store/modules/**`（状态）、`src/router/index.ts`（静态路由）、`src/permission.ts`（动态路由/权限守卫）、`src/utils/request.ts`（axios 封装）。
- 请求规范：统一 `Authorization: Bearer <token>` + `clientid` 头；可选 `encrypt-key` AES 请求加密；`repeatSubmit` 防重复提交；返回 `R`（`code/msg/data`），`code!==200` 时统一弹错。
- 鉴权：Sa-Token 登录态 + 菜单/按钮权限码（`@SaCheckPermission` 后端、`v-hasPermi` 前端）。
- 新增量化页面统一挂 `src/views/quant/*`，菜单经 `contract/menu` 事实源扩展，权限码沿用 `quant:*`（ADR-12）。

### 3.3 通信模式

- 前后端：HTTP REST（JSON），`/dev-api` 前缀由 vite 代理到后端 8080。
- 事件：进程内 Spring Event（`ApplicationEventPublisher` + `@EventListener`/`@TransactionalEventListener`），已落地事件契约 `contract/events/*.schema.json`。
- 实时推送：SSE `/resource/message`（统一消息推送，`message.transport=sse`）；Redis Pub/Sub 主题 `quant:market:broadcast`、`quant:risk:alert`。
- Dify：WebClient 消费 `text/event-stream`（`POST /v1/workflows/run`，Bearer `DIFY_APP_API_KEY`，ADR-11 方案 A 异步消费流式响应）。

### 3.4 数据模式

- MySQL（业务/研究/基础/盘口摘要/因子/质量/状态）＋ Redis（缓存/锁）＋ DuckDB（仅 Tick 与 K 线：30 分钟/日/周/月，ADR-9）＋ 对象存储（原始快照/附件，预留引用路径）。
- 迁移：Flyway（`db/migration/V*__*.sql`），禁止直改历史 SQL。
- 分库分表/多表：单表编辑用 `LambdaUpdateWrapper`；≤2 表查询用 MyBatis Plus；多表关联才在 XML 写 SQL（框架规则）。

### 3.5 部署模式

- Docker Compose 单机网络（ADR-10/11）：Spring Boot + MySQL + Redis + DuckDB(volume) + MinIO + Dify v1.16.1 + TradingAgents + xxl-job-admin，详见《详设_9_部署详细设计方案》。

## 五、数据库架构（DDL）

### 5.0 通用约定（全部业务表强制）

1. **主键**：`pk_id BIGINT NOT NULL COMMENT '主键（雪花ID）' PRIMARY KEY`，由 Hutool `IdUtil.getSnowflake(workerId, datacenterId).nextId()` 生成；**不使用**数据库 `AUTO_INCREMENT`。
2. **雪花参数**：workerId / datacenterId 配置在 YAML/env，见 §6.2。
3. **审计/追踪列**（主数据/配置类表）：复用 RuoYi `BaseEntity`（`create_by/create_time/update_by/update_time/remark`）；数据/日志类表用业务时间字段（`published_at/available_at/observed_at/occurred_at` 等）+ `create_time`。
4. **命名**：全部小写下划线；唯一键 `uk_<表短名>_<列>`；普通索引 `idx_<表短名>_<列>`；CHECK 约束 `ck_<表短名>_<列>`；外键 `fk_<表短名>_<列>`；表短名 = 去掉 `quantpf_` 前缀。
5. **枚举**：状态列用 `VARCHAR` + `CHECK` 约束（与既有 `quantpf_instrument` 风格一致），对应 Java 枚举（§6.3）。
6. **时间**：`DATETIME`（业务时间走 `DATETIME(6)` 以保留亚秒），统一 UTC 或统一服务器时区入库、展示层再转（《详设_1 §12.3》市场本地日期单独存 `DATE`）。
7. **字符集**：`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`。

### 5.1 数据源与来源组

```sql
-- 供应商/数据产品登记：供应商名称、账号类型、合同/订阅、服务周期、费用、到期、共享范围
CREATE TABLE quantpf_data_source (
    pk_id            BIGINT       NOT NULL COMMENT '主键（雪花ID）',
    source_code      VARCHAR(64)  NOT NULL COMMENT '数据源编码（如 TUSHARE_PRO / CLS_TELEGRAPH）',
    source_name      VARCHAR(128) NOT NULL COMMENT '数据源名称',
    vendor_name      VARCHAR(128) NULL     COMMENT '供应商组织名',
    account_type     VARCHAR(32)  NULL     COMMENT '账号类型',
    contract_ref     VARCHAR(128) NULL     COMMENT '合同/订阅标识',
    service_scope    VARCHAR(255) NULL     COMMENT '服务周期与共享/商业使用范围',
    fee_info         VARCHAR(255) NULL     COMMENT '费用说明',
    expiry_date      DATE         NULL     COMMENT '到期日',
    primary_source   TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '是否主源（1是/0否）',
    health_status    VARCHAR(32)  NOT NULL DEFAULT 'DRAFT' COMMENT '健康状态',
    status           VARCHAR(32)  NOT NULL DEFAULT 'DRAFT' COMMENT '生命周期状态',
    create_by        VARCHAR(64)  NULL     COMMENT '创建人',
    create_time      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_by        VARCHAR(64)  NULL     COMMENT '更新人',
    update_time      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    remark           VARCHAR(500) NULL     COMMENT '备注',
    PRIMARY KEY (pk_id),
    UNIQUE KEY uk_data_source_code (source_code),
    CONSTRAINT ck_data_source_status CHECK (status IN ('DRAFT','PENDING_CONFIRMATION','ACTIVE','DEGRADED','EXPIRING','EXPIRED','SUSPENDED','RETIRED'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='数据源/供应商/数据产品登记表';

-- 接口目录：数据产品下的具体接口及其历史范围/更新频率/延迟/额度
CREATE TABLE quantpf_data_source_interface (
    pk_id             BIGINT       NOT NULL COMMENT '主键（雪花ID）',
    source_id         BIGINT       NOT NULL COMMENT '数据源ID（关联 quantpf_data_source.pk_id）',
    product_code      VARCHAR(64)  NULL     COMMENT '数据产品编码',
    endpoint_name     VARCHAR(64)  NOT NULL COMMENT '接口名（如 trade_cal / fut_trade_cal / hk_tradecal）',
    field_summary     VARCHAR(1000) NULL    COMMENT '字段摘要',
    history_from      DATE         NULL     COMMENT '历史数据起始',
    history_to        DATE         NULL     COMMENT '历史数据截止',
```

### 6.2 雪花 ID 配置（Hutool Snowflake）

`ruoyi-admin/src/main/resources/application.yml`（env 优先，仿 `${X:${Y}}` 样式）：

```yaml
quantpf:
  snowflake:
    # 雪花算法 workerId（0~31），多实例部署时每实例唯一，通过环境变量覆盖
    worker-id: ${QUANTPF_SNOWFLAKE_WORKER_ID:1}
```

`quantpf-common` 装配 Bean：

```java
@Configuration
@ConfigurationProperties(prefix = "quantpf.snowflake")
public class QuantPfSnowflakeConfiguration {
    /** 雪花 workerId（0~31） */
    private int workerId = 1;
    /** 雪花 datacenterId（0~31） */
    private int datacenterId = 1;
    // getter/setter

    @Bean
    public Snowflake quantpfSnowflake() {
        return IdUtil.getSnowflake(workerId, datacenterId);
    }

    /** 主键自动填充：插入时若 pkId 为空则写雪花ID */
    @Bean
    public MetaObjectHandler quantpfMetaObjectHandler(Snowflake snowflake) {
        return new MetaObjectHandler() {
            @Override
            public void insertFill(MetaObject metaObject) {
                if (metaObject.getValue("pkId") == null) {
                    this.strictInsertFill(metaObject, "pkId", Long.class, snowflake.nextId());
                }
            }
            @Override
            public void updateFill(MetaObject metaObject) { /* 由 DB ON UPDATE 兜底 */ }
        };
    }
}
```

### 6.6 日志、异常与幂等

- **日志**：关键点用 `log.info/debug/warn/error` 打印业务上下文（如「采集任务 {taskCode} 状态 {status}，来源 {sourceCode}，异常 {errorCode}」）。开启 `@Slf4j`。
- **异常**：业务异常抛 `ServiceException`（底座 `org.dromara.common.core.exception.ServiceException`），统一走全局异常处理器；非空严禁空指针——所有外部字段用 `Objects.requireNonNull` / `Optional` / `StringUtils`（hutool）守卫。
- **幂等**：写接口要求 `Idempotency-Key` 头（或业务幂等键），以唯一键兜底（`uk_*_idempotency`）；重复键返回原结果、同键不同参数返回幂等冲突 `QPF-IDEMP-001`。
- **事件**：用 `ApplicationEventPublisher.publishEvent(...)`（`@TransactionalEventListener(phase = AFTER_COMMIT)`）发布 §10 事件；事件字段含 `eventId/eventType/aggregateId/occurredAt/availableAt/schemaVersion/idempotencyKey/correlationId`。

## 九、关键业务流程落地细节

### 9.1 新闻监控 → 研究事件（§10，跨模块一/二）

```
1. XXL-JOB newsScanJob → MarketDataCollectionTask(RUNNING)
2. 采集适配器 → 保存原始快照（contentHash/externalId）→ 去重
3. 质量/授权/初步行业标的映射 → DataQuality + ResearchMaterial
4. 创建 ResearchTask（冻结点时 snapshotId）→ 发布 ResearchTaskCreatedEvent
5. Dify/TradingAgents 适配器调用 Workflow API（流式 SSE，WebClient）
6. 保存 AiResearchDraft（raw_response + schema 校验）
7. 校验引用/时间/授权/身份/冲突 → 失败 PENDING_REVIEW/CLAIM_UNVERIFIED；通过保存 ResearchEvent + EventEvidence + 版本
8. 发布 ResearchEventPublishedEvent（幂等键 + correlationId）
```

### 9.2 交易日历同步（§12）

- 适配器按「源接口 + 字段 Schema 版本」隔离：`trade_cal`/`fut_trade_cal`/`hk_tradecal`/`us_tradecal`/`fx_obasic` 各自保留原请求/响应。
- `is_open` 原始值与标准化布尔值**同时保存**；解析失败进 `INVALID`，不得默认开市。
- 期货首用 `fut_trade_cal`（GFEX 缺口走人工维护 `CN_FUTURE_GFEX`）；`trade_cal` 只作交叉核验。
- 商品种/经纪商绑定 `fx_obasic.classify/trading_hours/break_time` → `quantpf_fx_session_rule`，不伪造统一外汇日历。
- 冲突进 `quantpf_calendar_conflict`，不静默择一。

### 9.3 容量与用途资格（§15/§16）

- 容量评估确定性规则计算 `SUFFICIENT/LIMITED/HIGH_IMPACT/UNTRADEABLE/UNKNOWN`；`LIMITED` 限规模、`HIGH_IMPACT` 仅观察、`UNTRADEABLE/UNKNOWN` 禁止新开仓。
- 用途资格由 `dataQualityStatus × authorizationStatus × timeVisibilityStatus × instrumentStatus × marketSessionStatus × capacityStatus` 确定性组合，结果缓存 Redis（键 `quant:eligibility:{instrumentId}`，带版本）。
