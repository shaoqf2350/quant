| 项目 | 内容 |
|:---|:---|

| 主文档 | 《详设_1_数据与标的基础详细设计方案_代码落地指导文档.md》（以下简称「主文档」） |

| 落地范围 | 模块一「数据与标的基础」全部前端页面（`plus-ui/src/views/quant/**`）与对应后端字典支撑 |

> 本规范将「用户操作界面友好性 = 输入项最小化」固化为可施工、可验收的硬约束：**ID/编码后端生成、枚举/范围用下拉且事实源统一在后端、布尔用选择框**。目标是消除前端硬编码枚举与手填文本/数字 ID，使前端所有选项唯一来源为后端字典接口。

---

## 一、背景与结论

对照主文档功能点（§八 7 个页面）逐一核查，后端对「ID/编码后端生成」已基本到位（`pk_id` 雪花生成；`actionCode`/`eventCode`/`taskCode`/`issueCode`/`conflictCode` 后端生成；`source_code` 走后端 `DataSourceCatalog` + `/catalog` 接口），但**前端仍存在三类违背「输入最小化」的问题**：

1. **枚举硬编码在前端**：除 `source_code` 外，7 个页面的所有状态/类型枚举均在 `.vue` 内硬编码数组，与后端 Java 枚举（已含 `descOf()` 中文描述）重复维护。
2. **部分查询项用自由文本 / 手填数字 ID**：冲突状态、采集任务状态/类型、点时对象类型、周期（timeframe）、研究状态等用 `el-input` 手填；原始快照的 `sourceId/sourceGroupId` 用 `el-input-number` 手填。
3. **编码/版本仍暴露给用户输入**：`calendarCode`（`el-select allow-create` + 11 项前端预置）、`groupCode`（6 项前端预置）、日历 `version`、以及 `regionCode/venueCode/currency/timezone` 等自由文本。

本规范以「后端统一字典接口 + 前端动态拉取 + 输入最小化清单」一次性消除上述问题。

---

## 二、输入项最小化三原则（硬约束，全部前端页面强制）

| 原则 | 规则 | 反例（禁止） |
|:---|:---|:---|
| **ID / 编码后端生成** | `pk_id` 雪花、业务编码（`*Code`/`*Id` 类）一律后端生成，前端不提供输入框 | 手填 `sourceId`/`subjectId`/`materialIds` 的 `el-input-number` |
| **枚举/范围下拉 + 事实源后端** | 所有枚举、字典、有限范围值一律用 `el-select`，选项唯一来源为后端字典接口，前端**禁止**硬编码选项数组 | `.vue` 内 `const xxxOptions = [{ value, label }]` |
| **布尔选择框** | 布尔字段一律 `el-switch`（或 `el-checkbox`），不用文本「是/否」输入 | `el-input` 填 0/1、是/否 |

> 例外：纯查询用的「关键字模糊检索」（如标的代码/名称 keyword）保留 `el-input`；但**枚举型**查询条件必须下拉。

## 三、后端枚举字典接口规范

### 3.1 接口契约

统一字典接口（先改 `contract/openapi/quantpf-v29.yaml` 再写 Controller，遵循「先契约后代码」）：

```
GET /api/quant/dict/{enumName}
权限码：quant:data:query（只读，所有登录态角色可用）
返回：R<List<DictOptionVo>>

DictOptionVo {
  value: String      // 存库值（枚举 name()）
  label: String      // 中文文案（枚举 descOf()）
  description: String?  // 可选说明
  order: Integer?    // 可选排序
}
```

- 前端下拉渲染：`<el-option v-for="o in dict[enumName]" :key="o.value" :label="o.label" :value="o.value" />`。
- 列表/详情里的中文文案（`statusText` 等）继续由后端 `Vo` 返回（`toVo` 中 `descOf`），与下拉 `label` 共用同一事实源，保证「列表显示」与「筛选选项」永远一致。

### 3.4 后端实现规范

- 新增 `ruoyi-admin/src/main/java/com/quantpf/web/controller/QuantDictController`，`@RequestMapping("/api/quant/dict")`。
- 服务层 `DictService` 维护静态注册表 `Map<String, List<DictOptionVo>>`（或按需反射枚举），`label` 复用各枚举 `descOf()`；新增枚举 `list()` 提供 `[{value,label}]`。
- 对目录类（`DataSourceCatalog`/`SourceGroupCatalog`/`CalendarCodeCatalog`）额外提供 `GET /api/quant/dict/catalog/{catalog}`（或并入 `dict/{enumName}`），供「新增数据源/来源组/日历」下拉。
- **缓存**：字典结果缓存 Redis（键 `quant:dict:{enumName}`），版本随枚举代码变更失效；前端首次拉取后本地缓存，避免每页重复请求。
- **唯一性/合法性校验下沉后端**（已在 `DataSourceServiceImpl.add` 中 `DataSourceCatalog.of(...)` 校验，来源组/日历照此）：前端下拉即使被绕过，后端仍拒绝目录外编码。

## 四、前端落地规范

### 4.1 通用能力

- 新增 `src/composables/useDict.ts`（或 `src/api/quant/dict.ts` + 缓存）：
  ```ts
  // 拉取并缓存后端字典；页面内 const { options } = useDict('DataSourceStatus')
  export function useDict(name: string) {
    const options = ref<DictOption[]>([]);
    onMounted(async () => { options.value = (await getDict(name)).data ?? []; });
    return { options };
  }
  ```
- 下拉统一 `<el-select>` + `v-for="o in options"`；`filterable` 用于标的/数据源等长列表。
- **禁止**在 `.vue` 内声明 `const xxxOptions = [{ value, label }]`（验收 grep 检查，见 §五）。

## 五、验收门禁（前端输入友好性）

以下任一不通过，模块一前端不得验收：

1. **无前端硬编码枚举**：`plus-ui/src/views/quant/**` 内 `grep -rn "Options = \["` 仅允许空结果（含 `*Options` 数组）。
2. **无手填数字 ID**：查询/新增表单不得出现手填 ID 的 `el-input-number`（`subjectId` 等明确的高级过滤除外，须有中文说明）。
3. **无用户可输入编码/版本**：`calendarCode`/`groupCode` 等仅可下拉选择目录，`version` 不出现于表单。
4. **布尔一律 `el-switch`/`el-checkbox`**：不存在「是/否」「0/1」文本输入。
5. **字典事实源唯一在后端**：任一枚举值增删，前端无需改动即可生效（前端零硬编码）。

## 七、结论

本补充规范将「输入项最小化」从口头要求固化为可执行契约：后端以统一字典接口（`/api/quant/dict/{enumName}`）作为所有枚举/目录的唯一事实源，前端通过 `useDict` 动态拉取并全面替换硬编码与手填输入。落地后，模块一前端 7 页面的状态/类型/范围全部下拉化、ID/编码全部后端生成、布尔全部选择框化，实现「普通用户少输入、专业选项渐进暴露、事实源唯一在后端」的界面友好性目标。
