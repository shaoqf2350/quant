## 1. 文档说明：目的、读者、规范用语与全局不变量

### 1.1 文档目的

把总纲与技术分册确定的架构（Spring Boot 单体 + Dify/TradingAgents 外部研究引擎）落成一套可重复、可审计、可在 Windows 与 Linux 复用的 Docker 部署方案，覆盖：

```text
JDK21 / Spring Boot(jar) 服务
MySQL（业务主库）
Redis（缓存/锁/发布订阅）
DuckDB（嵌入式时序局部存储，Tick + K线）
MinIO（对象存储，原始快照/附件/Dataset 副本）
Dify（自托管，用户入口 + Workflow 编排）
TradingAgents（多智能体研究引擎，独立部署）
XXL-JOB（任务调度）
Vue3 前端（plus-ui，nginx 静态托管 + 反向代理）
```

### 1.2 读者与用途

- 运维/部署人员：按第 4–10 章完成环境准备、启动与初始化，按第 17 章验收；
- 研发人员：按第 8 章确认环境变量与 profile，按第 14 章处理降级与联调；
- 审核/安全人员：重点阅读第 5（网络）、第 11（环境隔离）、第 12（安全红线）、第 13（备份监控）。

### 1.3 规范性用语

| 词语 | 含义 |
|:---|:---|
| 必须 | 部署与施工必须遵守，违反即门禁不通过 |
| 应 | 默认遵守；偏离时形成架构决策记录（ADR） |
| 禁止 | 绝对不允许，属边界违规 |
| 建议 | 可调起始值，需按压测和实际硬件定稿 |
| 草稿 | 未经 Spring Boot 校验或人工确认的输出 |

### 1.4 全局不变量

1. Spring Boot 是唯一业务事实源、确定性主系统、风控主控、交易/账务主控；
2. Dify / TradingAgents 是外部研究引擎，输出一律视为 `AI_DRAFT`，经 Spring Boot 校验后才能进入业务状态；
3. Dify / TradingAgents 不得直连 QuantPF MySQL / Redis / DuckDB / 持仓 / 账户 / 风控 / 交易写接口；
4. 浏览器不得直连 Dify / TradingAgents API，不得持有其 Key；
5. Stage 1 永久禁止 LIVE / QMT / CTP / 真实委托，只允许本地 SIM / PAPER_MANUAL / PAPER_AUTO / SHADOW / READ_ONLY；
6. 环境必须至少区分 `dev / test / prod`，凭据与数据域按环境隔离；
7. 所有写操作幂等、可审计、可回放；敏感凭据不进代码仓/前端/日志/Workflow 节点明文。

## 2. 部署目标、范围与总体原则

### 2.1 一期部署目标

一期部署目标是支撑"数据监听 → 研究辅助 → 候选筛选 → 策略适配 → Paper/Shadow 模拟 → 复盘验证"闭环的**本地单机/单节点部署**，不包含：

- 真实券商/期货公司交易通道（QMT/CTP）；
- 集群/多活/跨机房容灾（单体架构，ADR-1，按模块预留拆分点即可）；
- 二期量价主导机会发现、完整图表工作台、高级订单流所需的高频存储与图形计算资源。

### 2.2 总体部署原则

| 原则 | 说明 |
|:---|:---|
| 单机 default、集群可选 | 一期按单节点部署；MySQL/Redis/Dify 保留扩展为独立集群的能力 |
| 数据域隔离 | QuantPF 业务域、Dify 运行域、TradingAgents 运行域三套数据/缓存/对象存储互不混用 |
| 网络最小暴露 | 仅前端入口对用户开放；Dify Console 仅内网/受控网络；其余仅容器内部网络可达 |
| 持久化外挂 | 所有有状态数据（MySQL/Redis/MinIO/DuckDB/Dify DB/日志）必须挂载到宿主机卷，删除容器不丢数据 |
| 版本固化 | 镜像版本、JDK、MQ、依赖锁定；禁止 `latest` 标签用于生产 |
| 幂等可重建 | 通过 Compose + Flyway + 初始化脚本，可在新机按文档快速重建 |

## 4. 宿主机前置条件与资源规划

### 4.1 资源要求

| 资源 | 最低 | 建议（一期） | 说明 |
|:---|:---|:---|:---|
| CPU | 4 核 | 8 核及以上 | Dify worker + Spring Boot + TradingAgents 并行研究时 CPU 吃紧 |
| 内存 | 16 GB | 32 GB | TradingAgents 多智能体并发 + Dify + JVM + MySQL/Redis、以及 Windows 上 WSL2 预留 |
| 磁盘 | 100 GB SSD | 512 GB SSD | MySQL/Redis/MinIO 数据 + K线（DuckDB）+ Dify DB/dataset + TradingAgents MongoDB + 日志 |
| 网络 | 内网可达 | 公网（模型供应商/数据源出口白名单） | Dify/TradingAgents 需访问模型 API；Spring Boot 需访问 Tushare 等数据源 |

### 4.2 Linux 前置（Docker Engine）

```bash
# 以 Debian/Ubuntu 为例；CentOS/RHEL 走 dnf 同版本即可
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
docker --version          # 应为 29.x
docker compose version    # v2.x
# 将部署用户加入 docker 组（避免误用 root 操作数据目录）
sudo usermod -aG docker "$USER"
```

### 4.3 Windows 前置（Docker Desktop 4.76.0）

1. 启用 **WSL2** 作为后端（`wsl --install`），并给 WSL 虚拟机预留充足内存/CPU（`.wslconfig` 里设置，见 4.4）；
2. Docker Desktop → Settings → General → Use the WSL 2 based engine；
3. Settings → Resources → 把部署目录所在盘符加入 File sharing（或用 WSL 内路径 `/home/...`，推荐后者，避免虚拟盘 IO 开销）；
4. 验证：`docker info` 正常、`docker compose version` 为 v2。

### 4.4 时区、时钟与系统参数

- 所有容器统一 `TZ=Asia/Shanghai`；
- 宿主机启用 NTP 时间同步，避免 HMAC 回调签名、JWT、飞天窗校验（详设 5 建议时钟偏差窗口 ≤ 5 分钟）因时差失败；
- Linux 生产建议提升打开文件数（MySQL/Java）：`ulimit -n 65535`；`vm.max_map_count` 若启用 Elasticsearch/Weaviate 需 `sysctl -w vm.max_map_count=262144`。

## 5. 网络、端口与数据域隔离

### 5.1 端口规划（宿主映射）

| 宿主端口 | 服务 | 容器内端口 | 暴露范围 | 备注 |
|:---:|:---|:---:|:---|:---|
| 80 / 443 | nginx（前端 + 反代） | 80 / 443 | 用户 | 网关唯一入口 |
| 8080 | spring-boot | 8080 | 仅容器内网 | 由 nginx `/prod-api` 反向代理 |
| 3306 | mysql | 3306 | 仅容器内网/本机 | 不建议对公网开放 |
| 6379 | redis（QuantPF） | 6379 | 仅容器内网 | 与 TradingAgents Redis 分机/分端口 |
| 9000 / 9001 | minio API / Console | 9000 / 9001 | 内网/本机 | Console 受控访问 |
| 8090 | xxl-job-admin | 8080 | 内网/本机 | 调度中心 Web |
| 9999 | xxl-job executor | 9999 | 仅容器内网 | 由 Spring Boot 内嵌开启 |
| 8088 | dify web console | 80 | 内网/受控 | 避开 80 端口冲突 |
| 5001 | dify api | 5001 | 仅容器内网 | 供 Spring Boot Adapter 调用 |
| 8000 | tradingagents backend | 8000 | 仅容器内网 | 供 Dify/Spring Boot 调用 |
| 3000 | tradingagents frontend | 3000 | 内网/本机 | 开发态；生产建议 `npm run build` 后静态托管 |
| 27017 | tradingagents MongoDB | 27017 | 仅容器内网 | TradingAgents 自有 |
| 6380 | tradingagents Redis | 6379 | 仅容器内网 | 与 QuantPF 6379 隔离 |

> **重要冲突提示**：TradingAgents-CN 默认也使用 Redis 6379 与 MongoDB 27017，README 与 `.env.example` 均如此。若与 QuantPF 同机部署，必须为 TradingAgents 单独启用 Redis 实例（宿主 6380），否则会争夺同一 6379 导致 key 冲突。MongoDB 27017 无冲突，但建议改为非默认端口并加认证。

### 5.2 host 网络 vs bridge 网络（关键平台差异）

- 仓库自带的 `RuoYi-Vue-Plus/script/docker/docker-compose.yml` 使用 `network_mode: "host"`。**host 网络仅 Linux 下可用**；
- **Docker Desktop for Windows/Mac 对 Linux 容器不支持 host 网络**，必须改为自定义 **bridge 网络 + 端口映射**；
- 因此本详设统一采用 `qpf-net` bridge 网络，保证 Windows / Linux 行为一致；服务间用容器名互访（`mysql`、`redis`、`spring-boot`、`dify-api`、`tradingagents`）。

### 5.3 数据域隔离与访问白名单

| 来源 | 目标 | 策略 |
|:---|:---|:---|
| 用户浏览器 | Spring Boot | 允许（经 nginx，QuantPF 登录态） |
| 用户浏览器 | Dify / TradingAgents API | 禁止（业务链路） |
| Spring Boot Adapter | Dify API | 白名单 + TLS + 服务端 Key |
| Dify | TradingAgents Adapter | 白名单 + 指定端点 |
| Dify / TradingAgents | QuantPF MySQL / Redis / DuckDB / Paper 写接口 | 禁止 |
| Dify / TradingAgents | 模型 / 数据供应商 | 仅批准出口域名/IP |

## 6. 逐组件部署方案

### 6.1 JDK 21（构建机与运行镜像）

- 构建机（可宿主机或临时容器）：JDK 21 + Maven，产物 `ruoyi-admin/target/ruoyi-admin.jar`；
- 运行镜像基线（沿用仓库 Dockerfile）：`bellsoft/liberica-openjdk-rocky:21.0.12-cds`，或使用 `eclipse-temurin:21-jre`；
- 运行 JVM 建议参数：

```text
-Xms2g -Xmx4g
-XX:+UseZGC
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/ruoyi/server/logs
-Djava.security.egd=file:/dev/./urandom
-Dserver.port=8080
```

> 调整为按实际内存：`-Xmx` 不超过容器内存上限的 75%，避免 OOM Killed。

### 6.2 Spring Boot 服务（jar）

**产物来源**：`RuoYi-Vue-Plus/ruoyi-admin` 经 `mvn clean package -P prod`（Linux）或 `.\mvnw.cmd clean package -P prod`（Windows）打包得到 `ruoyi-admin.jar`。

**镜像 Dockerfile（建议，多阶段）**：

```dockerfile
# ---- build ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /build
COPY . .
RUN mvn -pl ruoyi-admin -am clean package -DskipTests -P prod

# ---- run ----
FROM bellsoft/liberica-openjdk-rocky:21.0.12-cds
ENV TZ=Asia/Shanghai LANG=C.UTF-8 LC_ALL=C.UTF-8 JAVA_OPTS="-Xms2g -Xmx4g -XX:+UseZGC"
WORKDIR /ruoyi/server
RUN mkdir -p /ruoyi/server/logs /ruoyi/server/temp
COPY --from=build /build/ruoyi-admin/target/ruoyi-admin.jar ./app.jar
EXPOSE 8080 9999
ENTRYPOINT ["sh","-c","java -Djava.security.egd=file:/dev/./urandom -Dserver.port=8080 $JAVA_OPTS -jar app.jar"]
```

> 若采用仓库自带的单段 `ruoyi-admin/Dockerfile`（仅 `ADD target/ruoyi-admin.jar`），则先在宿主 `mvn package` 生成 jar，再 `docker build -t qpf-server ./ruoyi-admin`。两者等价，选其一并固化。

**裸机运行方式（可选，调试期）**：

```bash
# 前提取：已装 JDK21，且 MySQL/Redis/MinIO 已就绪
java -Dserver.port=8080 -Dspring.profiles.active=prod \
  -XX:+UseZGC -Xms2g -Xmx4g -XX:+HeapDumpOnOutOfMemoryError \
  -jar ruoyi-admin.jar
```

### 6.3 MySQL

- 镜像 `mysql:8.4`，字符集 `utf8mb4` / `utf8mb4_general_ci`；
- 关键参数：`--max_allowed_packet=64M --innodb_buffer_pool_size=1G --lower_case_table_names=1 --explicit_defaults_for_timestamp=true`；
- 数据目录持久化到卷；首次启动需注入初始化库 `quantpf` 与 `quantpf_init_sys_tables.sql`（见第 7 章）；
- 只对容器内网开放，root 密码与业务账号必须走环境变量，禁止使用仓库 dev 默认密码。

### 6.4 Redis

- 镜像 `redis:7-alpine`，`appendonly yes` + RDB，`maxmemory-policy allkeys-lru`（缓存）与业务锁键分别关注驱逐策略；
- 必须设置 `requirepass`，禁止无密码暴露；
- 用于：缓存（最新盘口/K线/持仓快照）、分布式锁（lock4j）、发布订阅（`quant:market:broadcast` / `quant:risk:alert`）。

### 6.5 DuckDB（嵌入式，非服务）

- **DuckDB 不是服务/端口**，无需容器。它是进程内 JDBC 数据库（ADR-9），由 Spring Boot 以 `jdbc:duckdb:/data/duckdb/quantpf.duckdb` 访问；
- 只需把宿主数据目录 `./data/duckdb` 挂载进 Spring Boot 容器，保持单写入者（单体架构天然满足）；
- 存储范围已收敛：**仅 Tick 与 K 线（30 分钟/日/周/月）**；其余全部入 MySQL（ADR-9，修订技术分册 26.3）；
- 备份 = 停写后拷贝 `.duckdb` 文件（或 `EXPORT DATABASE`），见 13 章。

### 6.6 MinIO

- 镜像 `pgsty/minio:RELEASE.2026-04-17T00-00-00Z`（或官方 `minio/minio` 同能力版本）；
- 端口 9000（API）/ 9001（Console）；数据 `/data`、配置 `/root/.minio` 外挂；
- 初始化命令 `server --address ':9000' --console-address ':9001' /data`；
- **必须更换默认账号**（仓库默认 `ruoyi/ruoyi123`，属不安全默认值），改用环境变量注入强密码；
- 用途：原始快照、附件、Dify Dataset 文档副本（受控、脱敏）；桶规划至少 `qpf-snapshots`、`qpf-dify-dataset`、`qpf-backups`。

### 6.7 前端 plus-ui

- 构建：`cd plus-ui && pnpm install && npm run build`，产物 `dist/`；
- 配置 `VITE_APP_BASE_API=/prod-api`（生产）、`VITE_APP_ENCRYPT=true`（接口加密，前后端 RSA Key 配对，详见 12.3）；
- 由 nginx 托管 `dist/`，并把 `/prod-api/` 反向代理到 `spring-boot:8080/`，转发时去掉 `/prod-api` 前缀（见 `script/docker/nginx` 现有反代约定）。

### 6.8 XXL-JOB（调度）

- `xxl-job-admin`（调度中心）独立容器，宿主 8090，内网/本机访问；执行器为 Spring Boot 内嵌 `quant-executor`，端口 **9999**（ADR-10）；
- SnailJob 已整体下线（ADR-10），QuantPF 与底座任务统一进 XXL-JOB，**禁止双栈调度**；
- 任务清单以总纲 16.8 为基线：`weeklyOpportunityScanJob`（默认周频）、`dailyScreeningJob`（可选日频）、`tradingLoopJob`（交易时段独立）。

### 6.9 Dify（自托管，独立数据域）

- 采用 Dify 官方 v1.16.1 的 Docker Compose 独立部署（与 QuantPF 分离，不混库、不混 Redis、不混对象存储）；
- 运行单元：`web(nginx)/api/worker/db(postgres)/redis/weaviate 或 sandbox/plugin_daemon/ssrf_proxy`（以 v1.16.1 官方 compose 为准）；
- 对外只暴露：Console（宿主 8088）与 Service API（5001，供 Spring Boot 调用）；内部 postgres/redis/weaviate 不暴露宿主；
- Spring Boot 侧 `DIFY_BASE_URL` 指向 `http://dify-api:5001`（或统一经 nginx `/v1`），认证 `Authorization: Bearer ${DIFY_APP_API_KEY}`；
- 首次初始化（详设 6 §15.1）：创建 `QuantPF-Dev/Test/Prod` 工作空间、配模型供应商凭据（不写入节点明文）、关闭匿名注册、备份并作恢复演练。

### 6.10 TradingAgents-CN（独立数据域）

- 基线 v3.0.0：**Python 3.11 + FastAPI（8000）+ Vue3（3000）+ MongoDB 7/8 + Redis**，自备数据库，与 QuantPF 隔离；
- 部署链路（参考 `TradingAgents-CN/README.md` 与 `.env.example`）：

```text
1. 准备 MongoDB（认证开启，authSource=admin）与独立 Redis（宿主 6380）
2. 填 .env：MONGODB_CONNECTION_STRING / REDIS_HOST:6380 / REDIS_PASSWORD
            / JWT_SECRET / ADMIN_DEFAULT_PASSWORD / 模型 API Key / TUSHARE 等
3. uv 或 pip install -r requirements.txt（Python 3.11）
4. uvicorn app.main:app --host 0.0.0.0 --port 8000   # 后端
5. cd frontend && npm install && npm run dev          # 前端（dev :3000；生产 npm run build 后静态托管）
```

- Spring Boot / Dify 通过受控 Adapter 以 `TRADING_AGENTS_BASE_URL=http://tradingagents:8000` 调用；**不向 TradingAgents 提供交易凭据、账户明细或数据库直连权限**；
- 超时、重试、降级由 Dify/Spring Boot 统一管理（详设 6 §14.3 / §19）。

## 7. 数据库初始化与 Flyway 迁移

### 7.1 初始化顺序（必须严格遵守）

```text
1. 建库 quantpf（utf8mb4）
2. 导入 RuoYi 系统表：script/sql/quantpf_init_sys_tables.sql（sys_*/gen_*/test_*）
3. 启动 Spring Boot → Flyway 自动迁移 db/migration/V1_0_0 ~ V1_9_0（quantpf_* 业务表）
```

- `quantpf_init_sys_tables.sql` 负责 `sys_* / gen_* / test_*` 基础表与初始化数据，**不创建 quantpf_\* 业务表**（脚本头部已明确），且为 `CREATE TABLE IF NOT EXISTS + INSERT IGNORE` 幂等，可重复执行；
- `quantpf_*` 业务表由 `db/migration/V1_*__*.sql` 经 Flyway 在应用启动时自动创建/升级，**不要手工建这些表**。

### 7.2 重要红线

- **禁止在生产把 `doc/schema.sql` 当初始化脚本**：它是 V21 遗留 DDL，采用旧 `qm_/qs_/qt_` 命名并含 `DROP TABLE IF EXISTS`，与当前 `quantpf_*` 授权 schema 冲突，会破坏数据；
- Flyway 迁移不可手工改动历史版本号与已执行脚本；结构变更走新增 `V1_10_0__*.sql`。

## 10. Windows 与 Linux 部署差异要点

| 事项 | Linux（Docker Engine） | Windows（Docker Desktop） |
|:---|:---|:---|
| 网络模式 | 可用 `host` 或 bridge | 仅 bridge（本详设统一 bridge） |
| 路径 | `/opt/quantpf` | 建议放 WSL 内 `/home/...`，避免挂载虚拟盘慢 |
| 卷权限 | 注意 mysql/redis 数据目录属主 UID 对齐 | 由 Desktop 映射，一般无需手动 chown |
| 裸机 jar 运行 | `systemd` 服务守护 | 建议仍进 Docker，或 `nssm`/计划任务 |
| 资源 | 直接可用全部内存 | 受 WSL2 `.wslconfig` 上限约束，需调大 |
| 时区 | `TZ=Asia/Shanghai` | 同左，并注意 Docker 内核时钟 |

## 12. 安全加固、合规红线与敏感信息治理

### 12.1 网络与访问

- 仅 80/443 对用户开放；Mysql/Redis/DuckDB/MinIO 不对公网暴露；
- Dify Console 限内网/VPN；Dify/TradingAgents 调用走容器内网 + 白名单 + TLS；
- 出口白名单：仅允许 Spring Boot/Dify/TradingAgents 访问获批数据源与模型供应商域名/IP。

### 12.2 认证授权

- 接口沿用 RuoYi Sa-Token，量化接口默认全部需登录态、无匿名访问；
- Kill Switch（`/risk/halt`）需授权；手动下单（尤其二期 REAL）需二次确认 + 审计；
- PAPER_AUTO 恢复需人工审批（详设 5 §7.4）。

### 12.3 密钥与加密

- 所有 S1 凭据走环境变量/密钥管理（KMS/Vault），**不进代码仓、前端、日志、Workflow 节点明文**；
- `api-decrypt` 前后端 RSA 密钥成对替换并由运维保管私钥；`jwt-secret-key` 生产替换；
- `qs_broker_config.password_encrypted` 等通道密码脱敏存储。

### 12.4 Stage 1 合规红线

- **严禁** 部署/启用 LIVE、QMT、CTP、`REAL_BROKER_ORDER`、`REAL_BROKER_CANCEL`（技术分册 §35.3、菜单事实源 forbiddenCapabilities）；
- 一期只允许 `SIM / PAPER_MANUAL / PAPER_AUTO / SHADOW / READ_ONLY`，订单只进平台内部 Paper 撮合，不进入交易所撮合/结算；
- 二期实盘属独立阶段：数据/软件授权、券商/期货公司接入、程序化交易报告/确认、安全审计、人工放行门禁全部完成后另行立项，不作为本详设范围。

## 14. 降级与故障恢复

| 场景 | 处理 |
|:---|:---|
| Dify 不可用 | Spring Boot 保留事实核验、确定性筛选、Paper、风控、审计主线；研究解释标记"待补充"，不伪造结论 |
| TradingAgents 不可用 | 降级为单模型研究草稿或标记待补充，不得冒充多智能体结果（详设 6 §14.3） |
| 行情源/数据源不可用 | 禁止基于过期/缺数据生成新开仓；已持仓按退出规则管理（总纲 5.5/5.6） |
| Redis 抖动 | 缓存可重建、锁可重试；写接口靠幂等键防重（技术分册 31.4） |
| MySQL 抖动 | 依赖显式事务 `FOR UPDATE` + CHECK/唯一键兜底；恢复后核对账实 |

恢复演练至少验证：核心服务重启后状态一致、Flyway 不重复执行、幂等键不二次生效、Kill Switch 可即时生效。

## 15. 性能与容量建议

- Spring Boot：虚拟线程已由 RuoYi 支持，SSE 长连接按并发调 `server.jetty.threads.max`（默认 20000 为上限，非必要不放大）；
- MySQL：`innodb_buffer_pool_size` 设为可用内存 50%，慢查询阈值 1s 并落库；
- Redis：`maxmemory` 限制 + `allkeys-lru`，锁定键勿用逐出策略；
- Dify/TradingAgents 并发上限建议（详见 5 §15.6）：全局 Dify 并发 2–4、单用户问答 10 次/分、单任务 20 次/时、单次超时 120–180s、输入/输出同时限字符与 Token；
- DuckDB：仅低频 Tick/K 线（≤30 分钟级）落 DuckDB，高频实时数据走 Redis 缓存，批量异步落库，避免单文件写放大。

## 16. 常见问题排查

| 现象 | 可能原因 | 处置 |
|:---|:---|:---|
| `server` 反复重启 Flyway 报错 | 手工建了 quantpf_* 或改过历史迁移 | 清空 Flyway 历史表 `flyway_schema_history` 与手工表，重跑迁移 |
| 前端接口加密/解密失败 | 前后端 RSA Key 不配对 | 同步重生成并替换 `VITE_APP_RSA_*` 与 `api-decrypt.*` |
| 调用 Dify 401 | `DIFY_APP_API_KEY` 或 env 分离错误 | 核对 `DIFY_BASE_URL`/Key 与工作空间 APK |
| TradingAgents 启动报 Mongo 连接失败 | MongoDB 未开认证或 `authSource` 错误 | 核对 `MONGODB_CONNECTION_STRING` 与 `authSource=admin` |
| Redis 键冲突/数据串扰 | TradingAgents 与 QuantPF 共用 6379 | 拆分实例（6380）并分库 |
| Windows 容器无法 `host` 网络 | Desktop 不支持 Linux 容器 host 网络 | 全部改用 bridge 编排 |
| MinIO 无法上传 | 桶不存在或无权限 | 用 `mc mb` 建桶并赋最小权限 |

## 18. 已确认决策与待确认事项

### 18.1 已确认决策

| 编号 | 决策 | 依据 |
|:---|:---|:---|
| 网络统一 bridge | Windows/Linux 一致、可移植 | Docker Desktop 不支持 Linux 容器 host 网络 |
| MySQL 8.4 / schema `quantpf` | 与仓库 compose 与 dev 配置一致 | 技术分册 26.3/33 |
| DuckDB 嵌入式、仅 Tick+K线 | 一批数据文件挂载，非服务 | ADR-9 |
| SnailJob 下线 → XXL-JOB 3.1.0 | 单一调度 | ADR-10 |
| Dify v1.16.1 自托管 | Workflow API + Bearer APK | ADR-11、详设 6 |
| TradingAgents-CN v3.0.0 独立部署 | FastAPI+Vue+MongoDB+Redis | ADR-13、详设 6 |
| JDK 21 + ZGC | 沿用仓库 Dockerfile | 技术分册 33.1 |

### 18.2 待确认事项（联调前固化）

- 生产环境实际 MySQL/Redis/MinIO 高可用与磁盘规划是否升级为独立节点；
- XXL-JOB 3.1.0 具体 admin 镜像 tag 与官方镜像仓库的最终确认；
- Dify 实际部署版本与 v1.16.1 的 Workflow 导出/API/回调兼容性核验（详设 6 §27）；
- TradingAgents 是否容器化封装为标准镜像，或保持进程组部署；
- 模型供应商与数据源出口白名单、调用限额与成本预算的定稿；
- 生产 SSL 证书、域名与 `/prod-api` 反代路径的最终约定。
