## 一、结论摘要

### 1. 总体判断

V23 已经从“后端技术方案”扩展为“后端 + 前端原型 + 数据库补充 + 菜单权限”的较完整设计，研究、筛选、策略、风控、回测、模拟盘、前端展示等主链路已经成形。

但当前版本**还不能直接作为代码仓库的无歧义实施规范**。它更适合作为“架构蓝图 + MVP 设计基线”，在进入代码仓之前仍需完成一轮 P0 级冻结，尤其是：

1. 文档结构和版本元数据统一；
2. 技术栈和 RuoYi 基线锁定到具体仓库/提交；
3. CTP/QMT 网关、实盘/模拟适配器选择机制落地；
4. 交易账务、订单回报、夜盘交易日、外部事务补偿明确；
5. 前端新增 API 全部补齐契约和 Controller/Service/Mapper 责任；
6. MySQL 脚本改为正式迁移方案，并完成 sys_menu/角色权限映射；
7. 回测数据口径、公司行为、退市、期货连续合约和手续费模型冻结。

### 2. 可操作性评分（相对评估）

| 维度 | 评价 | 说明 |
|:---|:---:|:---|
| 架构方向 | 7/10 | 单体多模块、确定性策略、风控前置、模拟盘优先，方向合理 |
| MVP 可实施性 | 6/10 | 股票 + 日线 + 模拟盘可以实施，但仍有若干接口和账务缺口 |
| 直接生成代码的明确度 | 4/10 | 有类名和部分代码，但缺少完整契约、状态、迁移、测试和外部通道细节 |
| 真实交易准备度 | 3/10 | QMT/CTP、回报幂等、对账、补偿、密钥和熔断仍未达到实盘条件 |

| 文档一致性 | 4/10 | 存在版本尾注、目录、章节位置、路径和模块命名等明显不一致 |

### 3. 建议的落地策略

不要一次性实现股票、期货、现货、实盘、AI、新闻、财报、盘口、逐笔和多策略组合。建议冻结为：

```text
阶段 0：技术基线 + 数据库迁移 + 认证/权限 + 可观测性
阶段 1：股票 + 日线 + 爆点策略 + 模拟盘 + 回测
阶段 2：标的池 + 信号 + 风控 + 前端驾驶舱
阶段 3：新闻/财报/基本面增强
阶段 4：期货 + CTP + 夜盘 + 移仓换月
阶段 5：QMT/真实账户 + 对账 + 小资金灰度
阶段 6：盘口/逐笔/组合归因/高级监控
```

实盘接入必须晚于阶段 1～4 的回放、模拟盘、故障演练和对账验收。

## 二、已经做得比较好的部分

1. **确定性策略优先**：明确 LLM 只能作为情绪、财报和点评辅助，不直接决定下单，方向正确。
2. **模拟盘优先**：V21 的交易日历和模拟撮合使 MVP 可以在无券商环境下闭环验证。
3. **bar+1 回测模型**：已明确避免同一根 K 线成交造成的前视偏差。
4. **基础命名统一**：`product_type`、`symbol`、`quantity`、`avg_entry_price` 等命名已经统一意识较强。
5. **风控前置**：交易执行前调用确定性风控闸门，并设计了信号幂等。
6. **前端补充有效**：V23 增加了驾驶舱、标的、新闻、财报、标的池、回测、持仓、QMT/CTP、监控等页面，以及页面/API/DDL 映射。
7. **对缺口有自我识别**：文档已列出 RuoYi 版本、CTP/QMT 通道、复权、密钥托管、数据源 SLA、survivorship bias 等待决策项。

### P0-2 技术基线仍未冻结

文档写的是 Spring Boot 3.5.x、Framework 6.2.x、Security 6.4.x，同时又要求以“RuoYi-Vue-Plus 官方 pom.xml”为准，并保留 Boot 4.x 的条件分支。

这对于代码仓并不明确，因为以下内容没有锁定：

- RuoYi-Vue-Plus 的具体版本/分支/提交号；
- JDK 发行版和补丁版本；
- MyBatis-Plus、Sa-Token、Redisson、XXL-JOB 的实际版本；
- Vue/Element Plus/ECharts 的 lockfile；
- Docker 基础镜像；
- MySQL、Redis、时序库的版本；
- 构建命令和 CI 版本。

改进：新增“技术基线锁定表”：

```text
ruoyi_repo_url
ruoyi_git_commit
java_distribution/java_version
spring_boot_version
mybatis_plus_version
sa_token_version
mysql_version
redis_version
node_version
pnpm_version
```

所有版本写入父 `pom.xml`、`package.json`、lockfile、Dockerfile 和 CI，不再使用“3.5.x”“6.2.x”这种范围版本。

### P0-3 Maven 模块、Controller 模块和代码仓路径不一致

文档的 Maven 模块中没有 `quantpf-web`，并且写明 Controller 位于 `ruoyi-admin`；但新增代码仓建议又写了：

```text
quantpf-web/.../DashboardController.java
quantpf-web/.../FinanceController.java
```

同时包结构又写成：

```text
ruoyi-admin → com.quantpf.web.controller.*
```

改进必须二选一：

- 方案 A：Controller 全部放在 `ruoyi-admin`，删除 `quantpf-web` 路径；
- 方案 B：新增正式 Maven 模块 `quantpf-web`，由 `ruoyi-admin` 依赖它，并明确 Controller 扫描、依赖方向和启动配置。

个人/小团队 MVP 建议采用方案 A，减少模块数量。

### P0-4 Paper/QMT/CTP 的适配器选择存在冲突

`BrokerAdapter` 以 `ProductType` 作为路由键，而：

- `PaperBrokerAdapter` 是 STOCK；
- `QmtBrokerAdapter` 也是 STOCK；
- 文档只说“按优先级处理”，没有定义优先级来源、运行时切换、账户隔离和故障回退。

这会产生最危险的错误：真实股票账户请求被错误路由到模拟盘，或者模拟盘请求进入 QMT。

改进：适配器路由键至少改为：

```text
(accountType, productType, brokerProvider, executionMode)
```

例如：

```text
(VIRTUAL, STOCK, PAPER, PAPER)
(REAL, STOCK, QMT, LIVE)
(REAL, FUTURE, CTP, LIVE)
```

并增加：

- 启动时路由冲突校验；
- 生产环境禁止默认 Paper 覆盖 Real；
- 真实交易必须显式 `executionMode=LIVE`；
- 配置变更需重启或版本化生效；
- 每个订单落库实际 adapter、broker、account 和 execution mode；
- 集成测试验证“模拟账户永不进入 QMT、真实账户永不进入 Paper”。

### P0-5 外部券商事务不能依赖 `@Transactional` 回滚

文档写移仓换月“平旧仓 → 开新仓”，并标注 `@Transactional`，平旧失败中止、开新失败回滚。

数据库事务不能回滚已经发送给 CTP/QMT 的外部交易请求。真实场景中可能出现：

```text
平旧成功 → 本地事务失败 → 新仓未开
平旧请求超时但券商实际成功 → 重试造成重复平仓
开新成功但本地回报丢失 → 系统误判失败再次开仓
```

改进：使用 Saga/补偿事务，不要描述成数据库回滚：

1. 创建 rollover plan；
2. 状态置 `PREPARED`；
3. 平旧仓；
4. 等待并确认成交；
5. 开新仓；
6. 逐步记录每个外部请求和回报；
7. 异常进入 `NEEDS_RECONCILIATION`；
8. 由人工/自动补偿处理。

### P0-6 订单状态机不足以处理真实回报

当前状态机主要是：

```text
PENDING → SUBMITTED → PARTIAL_FILL → FILLED
```

缺少：

- `ACCEPTED`；
- `CANCEL_PENDING`；
- `PARTIAL_CANCELLED`；
- `UNKNOWN`；
- `RECONCILING`；
- `REJECTED` 的券商错误码和可重试性；
- 回报乱序；
- 重复回报；
- 外部订单号/成交号幂等；
- 断线重连后的订单补拉。

改进：新增 `qt_order_event`，每次状态变化保存不可变事件：

```text
order_no
outer_order_id
outer_event_id
event_type
from_status
to_status
payload_json
event_time
received_time
idempotency_key
```

订单主表只保存当前快照；订单事件表保存完整轨迹；对账任务负责修正 `UNKNOWN` 状态。

### P0-7 夜盘和交易日语义没有落地闭合

`qm_trading_session` 只有开始时间、结束时间和 `is_night`，但期货夜盘跨自然日。例如夜盘在自然日 2026-10-01 开始，成交归属哪个交易日必须明确。

影响：

- 信号幂等的 `trade_date` 可能错误；
- 手续费、权益、结算和日收益归属可能错误；
- 移仓换月和交易日历判断可能错误；
- `paperDailyResetJob` 可能在夜盘后错误重置。

改进：增加统一 `TradingDayContext`：

```text
exchange
product_type
calendar_date
trading_date
session_id
session_start
session_end
timezone
is_night
```

`trade_date` 不允许直接使用 `LocalDate.now()`，所有订单、信号、成交、权益快照和策略表现都由 `TradingDayContext` 计算。

### P0-8 回测口径仍不足以保证结果可信

文档已经修复 bar+1 前视偏差，但仍将以下关键问题列为待决策或未完全实现：

- survivorship bias/退市处理仍是 P2；
- 复权口径仍是待确认；
- 期货连续合约、换月和复权/价差规则未完全冻结；
- 公司行为、停牌、涨跌停、分红、送股和除权除息数据血缘不足；
- 真实手续费、印花税、过户费、交易所费率和期货手续费模型没有版本化；
- 滑点模型只写“滑点仅开仓计入”，与卖出和期货实际成交不够一致；
- 日线回测与盘中实时策略的信号时间边界没有统一。

改进：新增 `BacktestDataSnapshot` 或数据版本字段：

```text
data_snapshot_id
price_adjustment_method
corporate_action_version
universe_version
fee_schedule_version
slippage_model_version
calendar_version
```

回测报告必须能复现“当时使用的标的宇宙、价格、公司行为、手续费、滑点和日历”。

## 四、P1 重要问题：不一定阻塞 MVP，但必须纳入实施计划

### P1-1 成交记录无法稳定支持账户和策略归因

`qt_trade_record` 当前没有直接的：

```text
account_id
account_type
strategy_id
strategy_code
signal_id
broker_config_id
```

虽然可以通过 `order_no` 关联订单，但 `order_no` 允许为空，外部成交回报也可能没有可靠的本地订单号。这样会影响：

- 虚拟/真实成交分开统计；
- 策略收益归因；
- 账户权益计算；
- 实盘对账；
- 多策略共享账户时的 PnL 分配。

改进：成交表直接保存账户、策略、信号和外部通道字段；多策略共享账户时新增 `trade_allocation` 分配表，明确成交归因规则。

### P1-2 策略表现表缺少“收益归因口径”

`qs_strategy_performance_daily` 记录了策略和账户，但没有规定：

- 一个账户多个策略如何分配现金；
- 共享持仓如何归因；
- 信号重叠时谁拥有成交；
- 手续费和滑点归属哪个策略；
- 手工订单是否排除；
- 资金存取、分红、保证金变化如何处理。

改进：增加 `performance_scope`、`allocation_method`、`included_order_source`、`capital_flow`、`attribution_version`，并制定统一策略归因规则。

### P1-3 标的池评估字段缺少基准和价格时点

仅保存 T+1/T+3/T+5/T+10 收益不够，还需要：

```text
entry_reference_time
entry_reference_price
exit_reference_time
exit_reference_price
benchmark_symbol
benchmark_return
price_source
calendar_version
evaluation_version
```

否则不同数据源、停牌、涨跌停和跨市场交易日下，命中率无法复核。

### P1-4 财报原始数据使用 `data_json`，不利于稳定查询和校验

`qf_financial_statement.data_json` 适合保存原始快照，但不适合作为所有查询的唯一来源。

改进为“双层模型”：

- 原始层：原始 JSON、来源、抓取批次、原始哈希；
- 标准层：收入、净利润、现金流、资产、负债等强类型字段；
- 分析层：因子、AI 结论、同业对比。

新增数据血缘字段：

```text
source_record_id
source_fetch_batch_id
raw_hash
schema_version
restatement_version
```

### P1-5 新闻和 AI 结果缺少可复现信息

建议为新闻分析和财报分析增加：

- prompt_version；
- model_version；
- input_snapshot_hash；
- output_schema_version；
- temperature/top_p；
- token usage；
- 分析重试次数；
- 人工复核状态；
- 安全过滤结果。

AI 输出必须经过 JSON Schema 校验，不能直接把自由文本转换成交易信号。

### P1-6 数据源设计缺少统一采集框架

当前按 Tushare、EastMoney、CLS、Sina、AKShare 等分别描述，但没有统一定义：

```text
DataSourceAdapter
DataFetchRequest
DataFetchResult
RateLimiter
RetryPolicy
CircuitBreaker
RawPayloadStore
DataQualityChecker
```

建议统一采集框架，所有采集任务都记录：

- source_code；
- request_id；
- fetch_time；
- latency；
- response_status；
- record_count；
- raw_hash；
- error_code；
- retry_count；
- fallback_source。

### P1-7 API 设计缺少可直接生成代码的契约

V23 增加了 API 路径，但仍缺少：

- 请求 DTO 完整字段和类型；
- 响应 VO 完整结构；
- 分页返回统一格式；
- 错误码和 HTTP 状态映射；
- 排序/筛选语法；
- 日期和时区格式；
- 幂等键；
- 乐观锁字段；
- OpenAPI/Swagger 文件；
- WebSocket 消息 JSON Schema。

改进：先写 `openapi/quantpf-v23.yaml` 和 `event-schema/*.json`，再生成 Controller/DTO/前端 API 类型。

### P1-8 MySQL 脚本还不是正式生产迁移

当前补充脚本有以下问题：

1. 脚本主动 `CREATE DATABASE` 和 `USE quantpf`，不适合多数 Flyway/Liquibase/容器迁移流程；
2. 菜单使用硬编码 `230000` 等 ID，存在冲突风险；
3. `quantpf_ui_menu` 只是事实源，没有直接完成 `sys_menu`、`sys_role_menu` 同步；
4. 依赖后续尚未实现的 `MenuSyncService`；
5. 使用 `ON DUPLICATE KEY UPDATE` 的旧 `VALUES()` 写法，后续应改为 MySQL 8 推荐写法；
6. 动态 `ALTER TABLE` 缺少版本记录、回滚策略和迁移测试；
7. 没有执行前置条件检查、迁移锁和执行审计。

改进：

- 使用 Flyway 或 Liquibase 版本迁移；
- 一个迁移只负责一个可回滚/可验证的变更；
- 由部署系统选择数据库，不在迁移脚本中 `CREATE DATABASE`；
- 菜单同步在 Java Migration/Bootstrap 中完成并有集成测试；
- 使用数据库自增或雪花 ID，不硬编码业务主键；
- 预发布自动执行迁移、回滚演练和 schema diff。

### P1-9 前端原型与生产前端之间仍有较大落差

HTML 原型用于交互和视觉参考是合理的，但目前不是生产前端：

- 没有真实 API 接入；
- 没有登录、动态菜单和权限；
- 没有 WebSocket/SSE；
- 没有表单校验；
- 没有真实/虚拟账户安全隔离；
- 没有大数据量表格、分页和虚拟滚动；
- 没有错误、超时、断线、过期数据处理；
- 没有 ECharts 真实数据转换层。

改进：将原型页面逐页拆为 Vue 页面验收卡，每张卡包含：路由、权限、API、DTO、加载状态、错误状态、空状态、实时事件和测试用例。

### P1-10 可观测性和审计仍不够落地

文档提到 Prometheus/Grafana，但没有明确：

- 指标名称；
- 标签基数控制；
- traceId 传播；
- 订单全链路日志；
- 审计表；
- 告警路由；
- 告警抑制；
- 值班和升级策略；
- 数据库、Redis、网关、任务、AI 的 SLO。

建议新增：

```text
qa_audit_log
qt_order_event
qm_data_quality_issue
outbox_event
```

- MVP 先做股票/日线/模拟盘的方向。

### 2. 当前不能直接生成生产代码的部分

以下内容仍需要在代码仓开始前补齐：

1. 父 `pom.xml` 和前端 `package.json` 的确切版本；
2. 完整 OpenAPI；
3. 所有新增 API 对应 Controller/Service/Mapper/VO/DTO；
4. 数据库迁移版本和回滚策略；
5. RuoYi 菜单、角色、按钮权限的正式同步方案；
6. 交易适配器路由键和环境隔离；
7. 外部订单回报和对账模型；
8. 夜盘交易日和时区模型；
9. 数据源统一采集框架；
10. 回测数据快照和可复现机制；
11. 多策略账户的收益归因；
12. 密钥管理和密钥轮换；
13. 审计表、事件表、Outbox 和告警路由；
14. 集成、回放、故障、压测和迁移测试；
15. 实盘灰度、限额和 kill switch 运行手册。

因此，当前结论是：

```text
可以直接开始搭建 MVP 骨架；
不能直接据此安全地生成并上线完整实盘代码。
```

## 八、最终验收门槛

### 设计门槛

- [ ] 文档只有一个版本尾注和一个目录；
- [ ] 技术栈锁定到具体版本/提交；
- [ ] 所有 P2 决策已转为 ADR；
- [ ] 模块依赖通过 Maven 构建验证；
- [ ] API、事件和错误码有机器可读契约。

### 数据库门槛

- [ ] 基础 DDL、V23 补充 DDL 和迁移脚本一致；
- [ ] 脚本可重复执行；
- [ ] 迁移可在测试库执行和回滚；
- [ ] 主键、唯一键、外键/逻辑关联和索引完成检查；
- [ ] 菜单和角色权限可以初始化。

### 交易门槛

- [ ] Paper、QMT、CTP 路由不会冲突；
- [ ] 外部订单回报可去重、乱序处理和补拉；
- [ ] 订单、成交、持仓、账户可以对账；

### 前端门槛

- [ ] 每个菜单有正式路由、权限、API 和 DTO；

## 九、最终结论

V23 方案框架的业务覆盖面已经比较完整，作为架构蓝图和 MVP 规划是可用的；作为“直接生成完整代码并安全接入实盘”的规范仍不够明确。

最重要的改进不是继续增加更多页面，而是先把以下四个闭环做实：

```text
1. 交易状态闭环：订单 → 回报 → 成交 → 持仓 → 账户 → 对账
2. 数据复现闭环：数据源 → 原始快照 → 标准化 → 版本 → 回测报告
3. 安全控制闭环：权限 → 风控 → 审计 → 熔断 → 恢复审批
4. 工程落地闭环：版本 → API 契约 → DDL 迁移 → 代码 → 测试 → CI
```

完成 P0 修订后，可以正式启动“股票 + 日线 + 模拟盘”的 MVP 代码仓；在 P0 未完成前，不建议直接生成 QMT/CTP 实盘执行代码。
